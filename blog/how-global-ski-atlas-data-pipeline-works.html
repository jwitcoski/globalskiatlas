How the Global Ski Atlas Data Pipeline Works (For Non-Engineers)

September 12, 2026 · 7 min read

From OpenStreetMap extracts to GeoParquet, maps, wiki pages, and resort facts — a plain-language tour of how atlas data is built.

Global Ski Atlas looks simple when you zoom the interactive map: dots, polygons, lifts, and trail lines. Underneath that view is a repeatable data pipeline that starts with volunteer maps and ends in files your browser can draw quickly. This guide explains that path in plain language—OpenStreetMap to pipeline jobs to GeoParquet to the map, wiki, and stats pages—so non-engineers can trust what they are seeing and know how to improve it.

For a visual overview of the site and backend, see About. For downloads and the step list behind the datasets, see Download Data. For the resort-level numbers the pipeline computes, browse Ski Resort Facts.

Why open map data is the starting point

Ski resorts publish beautiful trail maps. Those maps are rarely comparable. One mountain counts glades; another counts only signed trails; a third markets “skiable acres” with fuzzy boundaries. Global Ski Atlas starts from OpenStreetMap (OSM) instead: a shared geographic database anyone can edit, with lifts and pistes tagged as real geometry.

OSM is not perfect. Popular U.S. and Alpine resorts tend to be richly mapped. Small municipal hills and remote areas lag. That unevenness is a feature you should understand, not a hidden flaw: when a resort looks thin in the atlas, the usual cause is incomplete tagging—not a conspiracy to hide terrain.

If you want to help, read how to tag a ski resort in OpenStreetMap. Fixes upstream become atlas updates after the next pipeline run.

The short version of the pipeline

In one paragraph: we download regional OSM extracts, find winter-sports areas, pull nearby lifts and pistes, enrich them with boundaries and names, compute statistics, export compact GeoParquet files, and publish those files for the website and researchers.

In practice the work is regional. Europe and North America are too large to process as one giant blob every time, so configuration splits continents into countries or sub-regions, then a combine step merges outputs into a global dataset. Download Data describes that regional strategy and the public Parquet files that result.

What each major stage is doing

You do not need to run the jobs to understand their jobs:

  1. Extract winter sports — Identify ski areas and winter-sport facilities in OSM.
  2. Nearby context — Pull OSM features within a few kilometers so buildings, roads, and related objects can support enrichment.
  3. Lifts and pistes — Capture lift lines and trail geometries with their tags (type, difficulty, name, and so on).
  4. Enrich — Attach administrative context, boundaries, and cleaner attributes for display.
  5. Analyze — Compute the statistics you see in comparison tools and facts pages: trail counts, elevation-related measures, area estimates, and similar fields.
  6. Parquet export — Write compact columnar files that keep geometry attached.
  7. Buffers and display helpers — Build mapping aids such as buffer polygons around ski areas.
  8. Names and translation fills — Improve English display names where needed.
  9. Elevation and contours — Attach elevation context used in analysis and cartography.
  10. CSV refresh — Regenerate tabular summaries with final fields.
  11. Combine regions — Merge regional outputs into the global set the site consumes.

That eleven-step outline matches the explanation on Download Data. Exact engineering details evolve; the idea stays stable: geometry in, comparable stats out.

GeoParquet in human terms

Parquet is a compact file format popular in data analysis. GeoParquet adds geography—points, lines, and polygons—so the same file can feed both spreadsheets-style tools and maps.

Why the atlas uses it:

  • Files stay smaller than bulky text formats for the same geometry.
  • Browsers and analysis tools can read only the columns they need.
  • One published snapshot can power the map, research downloads, and derived products.

On Download Data you will typically find ski-area files (raw and analyzed), lifts, and pistes. Analyzed ski areas feed much of what the Online Atlas and stats experiences summarize. Lifts and pistes feed the lines you see when you zoom into a mountain.

From files to the map you click

The public site is largely a static frontend with interactive map views. As described on About, maps are powered by MapLibre and load GeoParquet for client-side rendering. That means:

  • The basemap and ski layers can show thousands of areas without inventing a custom map per resort.
  • Zooming into a mountain reveals lift and piste geometry derived from OSM tags.
  • What you see is only as current as the last successful pipeline publish and the OSM edits that fed it.

When you compare two resorts in resort comparison, you are comparing fields computed by the same analyze step—not two marketing departments’ acreage claims. Ski resort stats explained defines how to read those columns carefully.

Wiki pages and “resort facts”

The Online Atlas wiki presents resort pages people can read like encyclopedia entries. Behind the scenes, page content and revisions live in a wiki service described on About. Mapped statistics still originate from the pipeline outputs.

Ski Resort Facts is the statistics-facing sibling: sortable, filterable summaries built from analyzed ski-area data. Use it when you want patterns across many mountains—largest trail counts, dense lift networks, beginner-friendly mixes—without opening fifty resort websites.

Together, map + wiki + facts answer three different questions:

  • Where is it, and what does the layout look like? → map
  • What is the story and structured page for this place? → wiki
  • How does it rank among peers on mapped metrics? → facts and comparison tools

What the pipeline cannot decide for you

Open data is honest about uncertainty. The pipeline cannot:

  • Guarantee a trail is open tomorrow.
  • Replace avalanche forecasts or resort patrol decisions.
  • Invent lifts that nobody mapped.
  • Resolve every naming conflict between local language names and marketing brands.

It also cannot freeze pass partnerships into permanent truth. Pass alignment articles such as Epic vs Ikon coverage are separate overlays that must be verified on official pass sites.

How often things update (conceptually)

Think in layers of freshness:

  • OSM edits — Happen whenever mappers save changes.
  • Pipeline runs — Batch jobs process regions and republish combined files; large continent runs can take many hours.
  • Website deploy — Static pages and app code ship on their own cadence.
  • Wiki edits — Human page text can move independently of geometry.

If a brand-new chairlift is missing, the fix is usually: map it in OSM, wait for (or trigger) a data refresh, then confirm it on the atlas map. For tagging help, use the OSM how-to post linked above.

How researchers use the same files

The downloadable Parquet sets are not a different “research universe.” They are the same family of outputs the site uses, published for analysis in tools like Pandas, GeoPandas, and DuckDB. Common projects:

  • Counting downhill areas by country or U.S. state (how many ski resorts worldwide, U.S. state counts).
  • Ranking mapped terrain size (largest ski resorts).
  • Studying lift-type mixes (ski lift types explained).
  • Joining external partner lists to atlas IDs for pass research.

Always credit OpenStreetMap contributors and follow the license terms that apply to OSM-derived data.

A mental model you can reuse

When something on Global Ski Atlas surprises you, walk this chain:

  1. Is the geometry present in OSM?
  2. Did the pipeline pick it up as a ski area, lift, or piste?
  3. Did analyze compute the stat you expected?
  4. Is the website showing the latest published file?

That sequence turns “the map must be wrong” into a diagnosable question. Often the answer is a missing tag. Sometimes it is a centroid quirk. Occasionally it is a true data bug worth reporting.
